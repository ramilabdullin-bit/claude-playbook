# Детализация счёта — из документа-факта, не подгонкой под сумму

## Симптом

Итог акта верен (сверен с реальными счетами), а список позиций под ним
строится из ДРУГОГО источника и «подгоняется» под итог: сначала берутся
«хорошие» записи, а недостающие до квоты добираются по формальному признаку
(самые ранние отменённые, самые поздние, по дате создания). Числа сходятся,
поэтому никто не смотрит. Потом сотрудник задаёт единственный вопрос, который
такой алгоритм не выдерживает: «почему ты учёл заказ A, а заказ B — нет?»
Честный ответ — «потому что A создан раньше», и он неверен по существу:
факт (что склад реально собрал) никак не связан с датой создания.

Найдено 2026-09-14 в `logistics-agent/tools/billing.py`: квота
`doc_stats["Завершено"]` (507) заполнялась 481 неотменённым заказом МП +
26 самыми ранними из 29 отменённых. По документам склада собраны были 27 из
29 отменённых — и не те, что выбрал алгоритм: 3 заказа, которые сотрудница
ждала в акте, выпали, 2 не собранных — вошли.

## Как распознать у себя

- В коде есть `[:quota]`, `sorted(...)[:n]`, «добираем до N», «сперва X,
  при нехватке Y» — при формировании списка позиций под уже известную сумму.
- Итог и детализация тянутся из разных ручек/таблиц, и «сходимость» —
  единственная проверка.
- Сотрудник спрашивает про конкретную позицию, а объяснение сводится к
  порядку сортировки.

## Что делать

1. **Найти документ-факт** — объект, который создаёт исполнитель в момент
   выполнения услуги (документ этапа «Завершено» у склада, акт приёмки,
   скан, проводка). Именно он даёт и итог, и список — один источник на
   обе цифры (см. [[dashboard-one-metric-one-source]]).
2. **Список позиций = документы-факты**, обогащённые из второго источника
   (код заказа, артикул, цена) через ключ соответствия. Ключ проверить
   вживую на одной группе: `совпало N из N по полю X, 0 по полю Y`.
   Здесь: `doc_number` документа = `orders[].id` (внутренний id), НЕ
   видимый код заказа WB — 507/507 по `id`, 0 по `code`.
3. **Расхождения не прятать, а классифицировать.** После стыковки останутся
   ровно четыре класса, и у каждого должен быть явный ответ владельца:
   | Класс | Что это на самом деле | Решение (2026-09-14, logistics-agent) |
   |---|---|---|
   | документ есть, записи во втором источнике нет | запись «переехала» (WB перенёс заказ в другую поставку, склад собрал повторно) | считать только в последней поставке; здесь вычесть из итога |
   | запись есть со статусом «выполнено», документа нет | исполнитель не закрыл документ (подобрано, не отсканировано) | включать по данным МП, с пометкой «проверь» |
   | документ есть, но по внешнему признаку услуга не оказана | ЧЗ требуется (`"sgtin" in optional_meta`), кода нет, заказ не доставлен | не биллить; доставленный без кода — в акт с пометкой |
   | группа без этапа «Завершено» вовсе | исполнитель не закрыл задание | по записям МП, попросить закрыть |
   Каждый случай скрипт ПЕЧАТАЕТ отдельной строкой с кодом и причиной
   (`Исключён: …`, `Проверь: …`, `Внимание: …`), а системный промпт агента
   обязывает пересказать их сотруднику. Молчаливая подгонка — главный вред.
4. **Статусы брать все**, незавершённые — называть поимённо: исполнитель
   забывает менять статус, фильтр `status == finished` теряет реальную
   работу.
5. **Проверить по вопросу сотрудника**, а не по сходимости: взять те самые
   коды, про которые спрашивали, и показать, в какой класс попал каждый.
   Потом прогнать второго клиента с другим профилем (у нас: без
   маркировки/смешанный) — правило, верное на одном, ломается на другом
   (у Эвереста 32 маркированных заказа доставлены без скана ЧЗ — «нет кода →
   не биллим» отрезало бы реальные отгрузки; спасла оговорка «и не
   доставлен»).

## Как это делалось безопасно

- Правка — в `git worktree` рядом с боевым проектом
  ([[using-git-worktrees]]), запуск тестов из worktree тем же venv; бой не
  трогается, пока владелец не скажет «выкатывай». Портальный аккаунт для
  тестов — НЕ тот, под которым работает сотрудник (портал держит одну
  сессию на пользователя).
- Каждая версия акта — сотруднику/владельцу файлом (Telegram) с подписью
  «что изменилось и сколько», решения — по одному, с перепрогоном.
- Первый холодный расчёт по документам был 209с (пагинация по 50,
  последовательно) — страницы одной группы грузить параллельно
  (`ThreadPoolExecutor`), ответы кешировать на диске: 99с холодный, 34с
  повтор.

## Специфика портала customer.e-comportal.com (PIM/WMS), чтобы не искать заново

- ФБС-заказы с МП живут ТОЛЬКО в `/api/wms/groups` docflow 1 («Сборка
  задания FBS», вкладка Склад → «Задания»). `/copacking` («Задания на
  упаковку», бейдж FBO) — переупаковка/подготовка стока, к ФБС не
  относится; его «завершено» — ручная отметка менеджера.
- `id` группы ≠ `code` (`code` = `fbssupply_id`); `GET /groups/{code}` → 404,
  искать `POST /api/wms/groups {"search_string": "WB-GI-…"}`.
- Документы: `GET /api/wms/groups/{id}/docs/page?doctype_id=<из doc_stats>
  &index=-1&limit=50&offset=N` (limit > 50 не принимает). Один документ =
  один заказ = 1 шт; `completion_status` `processed|cancelled_picking|
  cancelled_scanning|not_found_*`; `doc_number` = `orders[].id` из
  `/api/marketplace/orders/wb?fbssupply_id=<code>`; `order.wms_id` — id
  ПОЗИЦИИ документа Подбора, не документа.
- `docs_total` считает документы Подбора, `Завершено.quantity` — закрытые;
  разница = подобрано без закрывающего документа (через API не достать).
- Маркировка: `required_meta` у WB всегда `[]`, требование ЧЗ — `"sgtin"` в
  `optional_meta`; факт скана — `kiz_code`/`kiz_code_status == INTRODUCED`.
  Признака «подлежит маркировке» в карточке товара нет (только ТН ВЭД).
- У группы нет времени завершения (`changed == created`); время факта —
  только в документах (`doc.changed`, `positions[].fulfillment.created`).
