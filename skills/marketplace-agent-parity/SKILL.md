# Держать паритет возможностей между маркетплейс-агентами

Когда один сервис обслуживает несколько маркетплейсов РАЗНЫМИ наборами
инструментов и РАЗНЫМИ системными промптами (пример: Ozon-агент
`_TOOL_CMDS` vs WB-агент `WB_TOOLS` в `ozon-agent/webapp.py`, два отдельных
блока промпта), возможности неизбежно расходятся. Владелец натыкается на
дыру, только когда упрётся, и бесится, что «агенты должны синхронизироваться
по скилам». Точечный фикс по одной дыре = whack-a-mole и повторные вспышки.

## Правило

1. **Паритет ДВУСТОРОННИЙ.** Не только «вторичный до основного». Основной
   тоже может не иметь того, что есть у вторичного (реальный случай:
   у WB был топ карточек по выручке `wb_read.py sales`, у Ozon — нет).
2. **Сначала МАТРИЦА, потом порт.** Не чинить по одной. Составить таблицу
   «возможность (функция, не имя файла) → есть у A? / есть у B?», показать
   ВСЕ пробелы разом, портировать недостающее в обе стороны одним проходом.
3. **Новое умение → сразу всем.** Любая новая команда/скрипт/правило
   промпта добавляется у ВСЕХ маркетплейс-агентов в том же изменении
   (и в tool-список, и в промпт), иначе снова разъедутся.

## Как делать аудит (read-only)

Перечислить для каждого агента: список инструментов (развернуть
`_TOOL_CMDS`/`WB_TOOLS` в реальные скрипты, из docstring — что делает) и
блок системного промпта. Свести в матрицу функций. Проверить и уровень
allow-list: команда может СУЩЕСТВОВАТЬ в скрипте, но быть недоступной
агенту, если её нет в allow-list (реальная грабля: `baseline.py top`
написали, а в `_TOOL_CMDS` был только `baseline.py sku *` — агент не мог
вызвать).

Типовые оси функций: чтение карточки; характеристики + анализ пробелов;
справочник значений атрибутов; конкуренты (ниша/бренды и по-карточке);
запросы/позиции; топ по выручке; продажи/остатки/финансы; аудит контента;
реклама (чтение и мутации); вопросы покупателей; репрайсинг/прайс-вотч;
предложение SEO/характеристик; заказ фабрике (видео/фото/рич); публикация
видео/фото/рич.

## Грабли реализации (ozon-agent, проверено 2026-09-04)

- **Правки одного webapp.py разными форками параллельно ЗАПРЕЩЕНЫ** — один
  файл, конкурентная запись, форк может зависнуть и ничего не записать.
  Сериализовать: один агент правит webapp.py, либо править самому в один
  проход с одним рестартом. Логика в отдельных скриптах
  (`propose.py`/`proposals.py`/`*_read.py`/`baseline.py`) — параллель-
  безопасна.
- **`allowedTools` матчит команду точно** — добавляя субкоманду, обнови
  и allow-list (`"baseline.py top *"` и `"baseline.py top"` обе формы).
- **Правки webapp.py требуют `systemctl restart ozon-agent-web`** (процесс
  держит промпт/тул-листы в памяти). Скрипты, запускаемые per-call
  (`billing`-подобные), перечитываются сами.
- **Часть «дыр» — не быстрый порт, а проект** (WB-мутации рекламы, Ozon-
  инструмент продаж/остатков/финансов требуют новой работы с API). Их
  выносить владельцу отдельным списком-решением, а не чинить молча.
- Различия, которые НЕ дыры, а свойства площадки: у WB нет рич-контента;
  у Ozon 1 артикул = 1 карточка, у WB 1 артикул = несколько nmID.
