# Таймаут на запрос — не таймаут на работу

Цикл по N объектам, в каждом — поход во внешний сервис с таймаутом и
повтором. Каждый запрос «защищён», а вся работа — нет: худший случай равен
`N × (таймаут + повтор)`, и его никто не считал.

## Чем это обошлось

21.09.2026, logistics-agent. Акт клиента не собирался НИКОГДА: 30 заданий,
у 26 портал не отдавал выгрузку; 30 с + повтор 90 с на каждое = ~50 минут при
таймауте чата 840 с. Два убитых запроса сотрудницы и три ночных сбоя прогрева,
пока остальные клиенты считались нормально — потому казалось «флаки, повтори».
Повтор не мог помочь: неуспехи не кешируются, каждый прогон платит заново.

## Правило

1. **Посчитай худший случай:** `N × (timeout + retry)` против внешнего дедлайна.
   Если больше — работа не завершится именно тогда, когда сервис деградировал.
2. **Бюджет на весь прогон** рядом с таймаутом на запрос: копится время,
   потраченное на медленные ответы (и на медленные УСПЕХИ тоже); исчерпан —
   остальные объекты сразу идут запасным путём, без попытки.
3. **Запасной путь обязан существовать и говорить о себе:** одна строка
   «сервис медленный, данные X добраны способом Y» в выводе, который увидит
   человек. Нет запасного пути — падать сразу с понятной причиной, а не через
   14 минут.
4. **Ищи висящий запрос инструментом, не чтением кода:**
   `pip install --target <tmp> py-spy && <tmp>/bin/py-spy dump --locals --pid <pid>`
   — URL виден в локальных переменных за 10 секунд.
5. **«У одного висит, у остальных ок»** — смотри, чем этот один отличается по
   объёму (N) и прогрет ли у него кеш; новый клиент = холодный кеш = полный
   худший случай с первого же запроса.
