# Код только под задачу, а не ради кода

**Когда применять:** в начале любой задачи - вставляй первым сообщением вместе с описанием задачи, это задаёт рамку на всю сессию. Когда агент начал «улучшать» соседний код, который ты не просил трогать. Когда агент предлагает первое попавшееся решение без сравнения с альтернативами.
**Источник:** Артемий Миллер, промпт №1 «Code to solve problems, not code for code's sake» (`training/source/promty/kod-tolko-pod-zadachu-a-ne-radi-koda.md`).

## Промпт

```prompt
Перед любым изменением кода ответь себе на 2 вопроса:

1. Это изменение реально решает поставленную задачу?
2. Это самое эффективное из известных решений?

Если на любой ответ «нет» или «не уверен» - остановись.
Не пиши код. Сначала: исследуй альтернативы, выбери лучшую, объясни почему.

Запрещено:
- Менять то, что не относится к задаче (drive-by рефакторинг)
- Добавлять «на всякий случай» (валидации, обёртки, абстракции под гипотетику)
- Делать «красивее» без влияния на корректность
- Брать первое пришедшее в голову решение, не сравнив с альтернативами

Правило: каждая строка нового/изменённого кода должна напрямую закрывать
требование задачи. Не можешь связать строку с требованием - удали её.
```

## Почему работает

LLM по умолчанию склонны добавлять: больше кода, больше абстракций, больше «защиты». Промпт переворачивает дефолт - заставляет агента вычитать и обосновывать каждую строку. На практике сокращает дифф в 2-3 раза.

## Адаптация под Контент-завод

- «Требование задачи» у нас = фаза плана в `plans/` + узел конвейера из `architecture/`. Строка кода, не привязанная к фазе, - лишняя.
- Особенно бьёт по соблазну «сразу заложить все 11 площадок»: узел одной площадки делается под одну площадку, адаптеры под остальные - отдельные фазы.
- Промпт-соседи: `prove-plan.md` (до плана), `self-check-before-done.md` (после реализации).
