# Три вопроса к плану до того, как писать код (+ критика тремя субагентами)

**Когда применять:** после того как агент написал план реализации, ДО начала кодинга. Каждый раз, когда план кажется тебе «вроде ок» - прогони через эти 3 вопроса. Если план большой или дорогой в откате - добавь второй заход: критика тремя параллельными субагентами в свежем чате.
**Источник:** Артемий Миллер, промпт №3 «Challenge Loop» (`training/source/promty/tri-voprosa-k-planu-do-togo-kak-pisat-kod.md`); второй промпт - из стартера `claude-code-starter` (бывший `plan-critique.md` этой папки, объединён сюда).

## Промпт 1. Три вопроса (быстрый фильтр, в том же чате)

```prompt
Перед тем как финализировать план, ответь на 3 вопроса:

1. РЕШАЕТ ЛИ ЭТО ПРОБЛЕМУ?
   Сопоставь каждый пункт плана с acceptance criteria из спеки.
   Если хоть один критерий не покрыт - план неполный.

2. ЭТО САМОЕ ЭФФЕКТИВНОЕ РЕШЕНИЕ?
   Найди: кто уже решал эту проблему? Какой подход выбрали?
   Назови 2-3 альтернативных подхода (включая найденные через research).
   Для каждого: плюсы, минусы, трудоёмкость.
   Обоснуй, почему выбранный подход лучше всех альтернатив.

3. ЕСТЬ ЛИ В ПЛАНЕ «КОД РАДИ КОДА»?
   Каждое изменение должно напрямую обслуживать acceptance criteria.
   Если изменение не привязано к задаче - удали.
   Drive-by рефакторинг - отдельная задача, не часть этой.

Только после прохождения всех 3 вопросов план можно считать готовым.
```

Это финальный фильтр перед тем, как сжечь часы на реализацию плохого плана. Один раз отловить дырку в плане - сэкономить день рефакторинга.

## Промпт 2. Критика тремя субагентами (взгляд со стороны, в новом чате)

Один агент в одном чате не может «посмотреть на свою работу со стороны». Новый чат + параллельные субагенты - это и есть взгляд со стороны.

Цикл: Клод пишет план в `plans/YYYY-MM-DD-название.md` → ты открываешь **новый чат** → промпт ниже → возвращаешься к плану и правишь → только потом реализация.

```prompt
У меня есть первичный план реализации: [путь к файлу, например plans/2026-04-23-payment-form.md].

Задача:
1. Прочитай план целиком.
2. Прочитай .business/INDEX.md и связанные файлы - чтобы понять контекст проекта.
3. Запусти 3 параллельных субагента на глубокое исследование:
   - агент 1: проверь техническую реализуемость каждой фазы, найди риски и подводные камни
   - агент 2: проверь соответствие плана бизнес-целям из .business/, найди пробелы и противоречия
   - агент 3: сделай ревью UX/пользовательского сценария - где пользователь может застрять, что непонятно
4. Собери их выводы в один отчёт с конкретными правками: что добавить, что убрать, что переформулировать.
5. Покажи мне отчёт. Я решу какие правки принять, и попрошу тебя обновить файл плана.

Всегда отвечай на русском.
```

Что делать с отчётом: критика обоснована → обнови план; промах (агент не понял контекст) → пропусти; поднимает новый вопрос → в «Открытые вопросы» плана. Не делай все правки разом - по пункту, решение «да / нет / позже» на каждый.

## Адаптация под Контент-завод

- «Acceptance criteria из спеки» у нас = DoD фазы в `plans/` (исполняемая команда с негативным случаем) и требования из `idea/`.
- Агент 3 во втором промпте для завода смотрит не на UX сайта, а на путь основателя: утренний ввод сырья → вечерний отчёт → одобрение публикации флагом `--approved`.
- Порядок: три вопроса всегда; субагенты - для планов узла публикации, биллинга и всего, что пишет живым людям.
- Правки в план вноси через `notes-in-plan.md`, а не пересказом в чате.
