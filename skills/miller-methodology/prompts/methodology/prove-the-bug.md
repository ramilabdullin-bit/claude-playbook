# Докажи, что баг настоящий, или не трогай код

**Когда применять:** когда агент начинает «находить и исправлять баги», которые ты его не просил искать. Когда видишь, что в дифф попадают изменения «для красоты» или «на всякий случай». При code review ИИ-кода.
**Источник:** Артемий Миллер, промпт №6 «Prove the Bug is Real» (`training/source/promty/dokazhi-chto-bag-nastoyaschii-ili-ne-trogai-kod.md`).

## Промпт

```prompt
Для КАЖДОГО найденного бага ответь:

1. Это РЕАЛЬНЫЙ баг или false positive?
2. Можешь ли ты доказать, что баг воспроизводится? Опиши конкретный сценарий: вход → ожидание → реальное поведение.
3. Если не можешь доказать - это НЕ баг. Не трогай код.

ПРАВИЛО: не исправляй код «для красоты» или «на всякий случай».
Исправляй ТОЛЬКО доказанные баги, которые реально влияют на функциональность.

Каждый «фикс» без доказательства = риск ввести новый баг.

Если сомневаешься между «исправить» и «оставить» - оставь.
```

## Почему работает

ИИ любит «улучшать» работающий код, добавляя баги. Это главный анти-overfix. Если баг нельзя доказать - его нет.

## Адаптация под Контент-завод

- Применять к отчётам ревьюера в ночном цикле (`/goal`, оркестратор): ревьюер находит «баги» пачками, чинить только доказанные.
- «Сценарий воспроизведения» для завода = конкретный входной файл сырья + ожидаемый пост + реальный вывод; складывать в `tests/fixtures/`.
- Ошибки в текстах постов (тон, канцелярит) - не баги кода; их чинить правилами в `.business/assets/voice.md`, а не патчем генератора.
