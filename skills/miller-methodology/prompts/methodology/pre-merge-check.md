# Что мы сломали: проверка перед слиянием ветки

**Когда применять:** ОБЯЗАТЕЛЬНО перед мержем любой ветки. После любого изменения, которое затрагивает интерфейсы, API, типы или контракты. Когда трогаешь файл, от которого зависят другие.
**Источник:** Артемий Миллер, промпт №7 «Impact Analysis» (`training/source/promty/chto-my-slomali-proverka-pered-sliyaniem-vetki.md`).

## Промпт

```prompt
ОБЯЗАТЕЛЬНАЯ ПРОВЕРКА ПЕРЕД МЕРЖЕМ:

1. РЕГРЕССИЯ
   Какие модули/функции зависят от изменённых файлов?
   Запусти ВСЕ тесты проекта (не только текущей фазы).
   Если что-то сломалось - это приоритет №1.

2. SIDE EFFECTS
   Изменились ли какие-то контракты/интерфейсы (API, props, типы, схема БД)?
   Если да - кто их использует? Все ли потребители обновлены?

3. THINK AHEAD
   Какие проблемы эти изменения могут вызвать через неделю/месяц?
   Edge cases, которые мы не протестировали?
   Что произойдёт с: нулевыми данными? Огромными данными? Конкурентными запросами?
   Что если пользователь сделает что-то неожиданное?

4. COMPATIBILITY
   Сохранена ли обратная совместимость?
   Нужны ли миграции данных?
   Нужен ли feature flag для постепенной раскатки?

Без прохождения всех 4 пунктов - не мержим.
```

## Почему работает

По опыту автора 75% ИИ-агентов ломают ранее работавший код. Это главный страховочный пояс. Без него о регрессии узнаёшь от пользователей.

## Адаптация под Контент-завод

- «Контракты» у нас = формат сырья на входе узла, формат поста на выходе, схема очереди и журнала публикаций. Изменил формат - проверь все адаптеры площадок.
- Пункт 4 «feature flag» для завода = отправляющая часть рождается выключенной; любая новая площадка сначала пишет в черновики, публикация только с `--approved`.
- Прогонять вместе с `CLAUDE.md` «перед push - билд и линтер».
